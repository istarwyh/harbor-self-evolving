## 后续版本沿用的格式

开始验证前，将[发布图集模板](TEMPLATE.md)复制到对应版本的 `README.md`，填写本次改动与准备验证的场景；验证过程中及时保存关键状态，结束后补齐实际结果。可参考 [0.9.2 图集](v0.9.2/README.md)，不要照抄旧版的成功结论。

```text
docs/releases/vX.Y.Z/
  README.md             # 变更摘要、操作步骤、结果、边界、来源
  screenshots/          # 编号 + 场景名；真实截图
```

有 UI 变更时建议选择 4–8 张最能说明变化的图，按实际场景增减，不为凑数重复页面。优先记录选择、提交前、执行中、结果或恢复等关键状态；非 UI 变更可以不截图，附对应测试/日志/提交链接并说明即可，不制造示意截图充当运行证据。存在真实的前后截图时才做前后对照。

每张说明记录日期（含时区）、被验证的版本/提交、验收环境、操作过程、预期与实际结果，以及 synthetic / controlled-model / real-provider / public-release 等证据类型；可以组合标注，不能把合成数据、受控模型和真实供应商混为一谈。版本/提交无法确认时如实写明，不推断为待发布版本。历史原图与本次补截分开标明；一张静态截图不证明完整状态转换。公开前检查可读性、凭据、个人信息和业务私有内容；优先在截图前隐藏敏感区域，必要的脱敏应注明，敏感原图不得进入 Git 历史或 Release 附件。保留未完成项及非阻塞警告，不为截图好看删除失败信息。

归档完成后，在对应 GitHub Release 放上图集入口和可下载的验证资料包。这里只是资料组织约定，不新增发布校验脚本、CI 门禁或人工审批，也不会自动运行模型、评测或发布。

## 发布交付清单

- [ ] 版本目录说明了本次改动，每项对应关键截图或测试/日志证据；非 UI 变更不强求截图。
- [ ] 证据的日期、版本/提交、环境、步骤、预期与实际结果、类型和边界已填写；待验证、失败和警告如实保留。
- [ ] 公开资料已检查可读性与敏感信息；图片使用 `screenshots/` 下的相对链接，源码/日志使用可追溯的在线链接，不依赖发布者的本机路径。
- [ ] 已更新本页版本索引；将版本目录（说明与截图）打包为 `harbor-X.Y.Z-verification.zip`，确认解压后说明中的图片可打开。
- [ ] 对应 GitHub Release 已附图集入口与资料包，公开图片、链接和下载可用；图集链接指向含归档文件的具体提交。发布后补资料可以新增文档提交，不移动已公开 tag、不覆盖安装包、不重发同版本。
- [ ] 按[发布指南](../npm-trusted-publishing.md)分别核对 npm、PyPI 和 Release，交付时分别报告包发布状态、资料归档状态与未验证范围。包已发布但资料未齐时，明确写“包已发布，验证资料待补”并列出缺项，不声称全部交付完成。

发布者在当次交付说明中逐项确认本清单，不勾选本索引中的共享清单，以免下一版误用旧状态。清单不触发额外校验程序或审批；只补文档/截图时不自动触发新版本发布。
